# Phase 2 — Current implementation status

**Branch:** `phase-2/auth-database-foundation`  
**Status:** Initial foundation committed; not yet validated against a running PostgreSQL instance or browser. Do not treat this as production-ready.

## Added in this branch

- PostgreSQL connection helper and a simple local `.env` loader.
- SQL migrations for organisations, users, role assignments, institution sites, authority scopes, invitations, audit events, and opaque database-backed sessions.
- Migration runner and one-time Super Admin bootstrap command.
- Password hashing and verification using Node's built-in scrypt implementation; opaque random session/invitation tokens; one-way token hashing.
- Server-side session authentication, HTTP-only cookie, CSRF token checks on protected mutations, role middleware, login throttling, invitation acceptance and password change.
- Initial Super Admin APIs for organisations, invitations, user status, user listing, and audit events.
- Staff sign-in page and navigation link; existing public v1 routes and JSON analysis history remain in place.
- Advisory analysis responses are marked `synthetic_demo` and `regulatory_use: false`; no analysis endpoint issues official notices.
- Basic Node tests for password and token helpers.

## Local setup (after pulling the branch)

1. Install a supported Node.js LTS release and PostgreSQL.
2. Copy `.env.example` to `.env`; set a local `DATABASE_URL`, bootstrap email/name/password and environment settings. Never commit `.env`.
3. Run `npm install` to install the new PostgreSQL driver and refresh `package-lock.json` for this branch. The lockfile has not yet been regenerated in this remote editing environment.
4. Run `npm run db:migrate`.
5. Run `npm run db:bootstrap-admin` once. The command refuses to overwrite an existing account.
6. Start with `npm run dev`; visit `/login` and sign in using the bootstrap account.
7. Run `npm test` and `npm run build`.

The bootstrap command is a one-time provisioning tool. Clear the bootstrap variables from your shell/secret environment after use. Do not run it on a production database unless the production deployment owner explicitly approves the action.

## API endpoints in this iteration

- `POST /api/auth/login`, `POST /api/auth/logout`, `GET /api/auth/me`, `POST /api/auth/change-password`, `POST /api/auth/accept-invitation`
- `GET /api/admin/organisations`, `POST /api/admin/organisations`, `PATCH /api/admin/organisations/:id/status`
- `POST /api/admin/users/invitations`, `GET /api/admin/users`, `PATCH /api/admin/users/:id/status`
- `GET /api/admin/audit-events`
- `GET /api/health`

New identity/admin routes require PostgreSQL. The existing public geocoding and demo analysis remain usable without a database. Existing analysis CRUD is still a local JSON demo store and is not yet scoped to accounts; do not store sensitive or official case material there. Phase 3 must replace this with tenant-scoped case and evidence persistence.

## Known gaps before Phase 2 can be called complete

- The package lock needs to be regenerated by `npm install`; this environment could not run npm because network access was unavailable.
- Browser build, migrations and API integration tests have not been run against a real database.
- Login throttling is per-process; production should use a shared rate limiter.
- Invitation delivery is not integrated with email; the Super Admin endpoint returns a one-time invitation token for secure manual delivery.
- Password recovery/email verification, organisation-specific identity verification, MFA, and session cleanup jobs are not yet implemented.
- The current v1 analysis CRUD remains shared local JSON and must not be treated as multi-user/private data.
- Authority/institution dashboards and scoped case APIs are Phase 3 work; this iteration provides authentication primitives and initial Super Admin APIs only.
- Review all security code and test access isolation before deploying or using real personal or government data.
